## 🎯 Resumen Ejecutivo

### ¿Qué es Xamanen?

**Xamanen** es una plataforma SaaS especializada en **digitalizar y automatizar el proceso completo de auditorías de seguridad ambiental, gestión de residuos peligrosos y cumplimiento normativo** para empresas que requieren certificación en Buenas Prácticas Ambientales (BPA).

### Problema que Resuelve

**Proceso tradicional de auditoría:**
- ⏱️ 7-10 días de entrega de informes
- 💰 $300-500 USD por auditoría (mano de obra + impresiones)
- 📄 Papeleo excesivo y propenso a errores
- 🗄️ Archivos físicos difíciles de gestionar
- ❌ 15-20% de errores humanos

**Con Xamanen:**
- ⚡ Entrega el mismo día
- 💵 $50 USD por auditoría
- 📱 100% digital con firmas electrónicas
- ☁️ Trazabilidad completa en la nube
- ✅ <2% de errores

### Visión del Producto

> "Ser la plataforma líder en Latinoamérica para la gestión integral de auditorías ambientales, transformando el cumplimiento normativo en un proceso simple, trazable y profesional que protege tanto al medio ambiente como a las personas."

### Mercado Objetivo

**TAM (Total Addressable Market):** $15.2B USD - Software de gestión ambiental global
**SAM (Serviceable Available Market):** $380M USD - Auditorías ambientales LATAM
**SOM (Serviceable Obtainable Market):** $3.8M USD - Alcanzable en 3 años

### Versión 2.0 (Propuesta) - Mejoras Críticas

#### 🔄 Refactorización de Arquitectura

**Objetivo:** Resolver deuda técnica crítica identificada

**Problemas a resolver:**
1. ❌ Memory leaks en 91% de los componentes
2. ❌ Código duplicado masivo (14 formularios casi idénticos)
3. ❌ vista-preliminar-checklist.component.ts: 2,069 líneas
4. ❌ CRUD incompleto (sin UPDATE/DELETE en checklists)
5. ❌ Sin AuthGuard en rutas
6. ❌ Token en localStorage (vulnerable a XSS)

**Entregas:**

1. **Sistema Dinámico de Checklists**
   - UN componente dinámico para todos los tipos
   - Configuración basada en JSON/DB
   - Reducción de 10,000+ líneas de código duplicado
   - CRUD completo (CREATE, READ, UPDATE, DELETE)

2. **Seguridad Mejorada**
   - AuthGuard en todas las rutas protegidas
   - Tokens en HTTP-Only cookies
   - HTTPS en todos los ambientes
   - Refresh tokens implementados

3. **Performance Optimizado**
   - Lazy loading en todos los módulos
   - OnPush change detection strategy
   - Bundle size reducido de 2MB a <500KB
   - Virtual scrolling en listas

4. **Testing Implementado**
   - Tests unitarios (>60% coverage)
   - Tests de integración
   - Tests E2E para flujos críticos

## ⚙️ Requisitos Funcionales

### RF-001: Autenticación y Autorización

**Prioridad:** 🔴 Crítica
**Épica:** Seguridad

#### RF-001.1: Login de Usuario
**Descripción:** El sistema debe permitir a los usuarios autenticarse con email y contraseña.

**Criterios de Aceptación:**
- ✅ El usuario ingresa email y contraseña válidos
- ✅ El sistema valida las credenciales contra la base de datos
- ✅ Si son válidas, genera un token JWT y redirige al dashboard
- ✅ Si son inválidas, muestra mensaje de error descriptivo
- ✅ El sistema bloquea cuenta tras 5 intentos fallidos consecutivos
- ✅ El token expira después de 8 horas de inactividad

**Validaciones:**
- Email en formato válido (regex)
- Contraseña mínimo 8 caracteres
- Protección contra SQL injection
- Rate limiting (10 intentos por IP por minuto)

### RF-003: Constancias de Visita Digitales

**Prioridad:** 🔴 Crítica
**Épica:** Documentación de Auditorías

#### RF-003.1: Crear Constancia de Visita
**Descripción:** El sistema debe permitir a técnicos generar constancias de visita con firma digital.

**Datos de Constancia:**
- Empresa (obligatorio, selector)
- Sede (obligatorio, selector filtrado por empresa)
- Fecha de visita (obligatorio, default: hoy)
- Hora inicio (opcional)
- Hora fin (opcional)
- Actividades realizadas (obligatorio, textarea)
- Firma digital del responsable (obligatorio)
- Nombre del firmante (obligatorio)
- Cargo del firmante (obligatorio)
- Observaciones (opcional)

**Flujo:**
1. Técnico selecciona empresa
2. Sistema carga sedes de esa empresa
3. Técnico selecciona sede
4. Sistema pre-carga datos de responsables
5. Técnico completa actividades realizadas
6. Técnico solicita firma al responsable de la empresa
7. Responsable firma en canvas digital (tablet/móvil)
8. Sistema genera PDF automáticamente
9. Sistema muestra vista preliminar
10. Técnico confirma y guarda
11. Sistema envía email al cliente (opcional)

**Criterios de Aceptación:**
- ✅ El canvas de firma funciona con mouse y touch
- ✅ El usuario puede limpiar la firma y volver a dibujar
- ✅ La firma se captura como imagen base64
- ✅ El PDF se genera con template profesional
- ✅ El PDF incluye logo de la empresa auditora
- ✅ El PDF incluye firma digital como imagen
- ✅ El PDF se almacena en el servidor
- ✅ Se puede descargar el PDF
- ✅ Se puede enviar por email

## 🚀 Requisitos No Funcionales

### RNF-001: Performance

**RNF-001.1: Tiempo de Carga**
- El sistema debe cargar la página inicial en menos de 2 segundos
- Las páginas subsecuentes deben cargar en menos de 1 segundo
- El bundle JavaScript inicial debe ser menor a 500KB

**RNF-001.2: Generación de PDFs**
- Un PDF de constancia debe generarse en menos de 3 segundos
- Un PDF de checklist debe generarse en menos de 5 segundos
- Un PDF de informe debe generarse en menos de 10 segundos

**RNF-001.3: Operaciones de Base de Datos**
- Las consultas de listado deben responder en menos de 500ms
- Las operaciones de escritura deben completarse en menos de 1 segundo

---

### RNF-002: Seguridad

**RNF-002.1: Autenticación**
- Contraseñas deben hashearse con bcrypt (cost factor 12)
- Los tokens JWT deben expirar después de 8 horas
- Los refresh tokens deben expirar después de 30 días
- Debe implementarse rate limiting (10 intentos de login por IP por minuto)

**RNF-002.2: Autorización**
- Todas las rutas deben estar protegidas con AuthGuard
- Los permisos deben verificarse en backend, no solo en frontend
- Los usuarios solo deben acceder a datos de sus empresas asignadas

**RNF-002.3: Protección de Datos**
- Todas las conexiones deben usar HTTPS
- Los tokens deben almacenarse en HTTP-Only cookies
- Los datos sensibles deben encriptarse en la base de datos
- Debe implementarse CSRF protection

**RNF-002.4: Auditoría**
- Todas las operaciones críticas deben registrarse (audit log)
- Los logs deben incluir: usuario, acción, timestamp, IP
- Los logs deben conservarse por al menos 1 año

---

### RNF-003: Escalabilidad

**RNF-003.1: Usuarios Concurrentes**
- El sistema debe soportar 500 usuarios concurrentes sin degradación
- El sistema debe poder escalar horizontalmente agregando servidores

**RNF-003.2: Almacenamiento**
- El sistema debe soportar almacenamiento de al menos 100,000 documentos
- Los archivos PDF deben almacenarse en storage externo (S3/similar)
- Debe implementarse política de retención de datos

**RNF-003.3: Base de Datos**
- La base de datos debe soportar al menos 1 millón de registros
- Debe implementarse indexación en campos de búsqueda frecuente
- Debe implementarse backup automático diario

---

### RNF-004: Usabilidad

**RNF-004.1: Responsive Design**
- El sistema debe funcionar en dispositivos móviles (tablets y smartphones)
- El sistema debe adaptarse a resoluciones desde 320px hasta 4K
- El diseño debe seguir principios de Material Design o similar

**RNF-004.2: Accesibilidad**
- El sistema debe cumplir con WCAG 2.1 nivel AA
- Todos los elementos interactivos deben ser accesibles por teclado
- Debe soportar lectores de pantalla

**RNF-004.3: Experiencia de Usuario**
- Las acciones deben tener feedback visual inmediato
- Los errores deben mostrarse con mensajes descriptivos en español
- El sistema debe tener ayuda contextual (tooltips)

---

### RNF-005: Disponibilidad

**RNF-005.1: Uptime**
- El sistema debe tener 99.5% de uptime (43.8 horas de downtime máximo al año)
- Debe tener ventanas de mantenimiento programadas fuera de horario laboral

**RNF-005.2: Recuperación ante Desastres**
- Debe implementarse backup automático cada 24 horas
- El tiempo de recuperación (RTO) debe ser menor a 4 horas
- El punto de recuperación (RPO) debe ser menor a 24 horas

---

### RNF-006: Compatibilidad

**RNF-006.1: Navegadores**
- Debe soportar Chrome 90+, Firefox 88+, Safari 14+, Edge 90+
- Debe degradar gracefully en navegadores no soportados

**RNF-006.2: Dispositivos**
- Debe funcionar en Android 8+
- Debe funcionar en iOS 13+
- Debe funcionar en Windows 10+, macOS 10.15+

---

### RNF-007: Mantenibilidad

**RNF-007.1: Código**
- El código debe seguir guías de estilo (ESLint, Prettier)
- El código debe estar documentado con JSDoc
- El código debe tener cobertura de tests >60%

**RNF-007.2: Monitoreo**
- Debe implementarse logging centralizado
- Debe implementarse monitoreo de errores (Sentry o similar)
- Debe implementarse monitoreo de performance (New Relic o similar)

## ⚠️ Dependencias y Riesgos

### Dependencias Técnicas

| Dependencia | Impacto | Mitigación |
|-------------|---------|------------|
| **Servicio de Email** | Si falla, no se envían constancias | Implementar cola de reintentos + backup SMTP |
| **Almacenamiento S3** | Si falla, no se guardan PDFs | Implementar almacenamiento local de respaldo |
| **MongoDB/MySQL** | Si falla, app no funciona | Implementar réplicas + backup automático |
| **Librería signature_pad** | Si tiene bug, no funciona firma | Tener alternativa (canvas nativo) |
| **pdfmake** | Si tiene bug, no se generan PDFs | Evaluar alternativa (Puppeteer, wkhtmltopdf) |

### Apéndice A: Glosario de Términos

| Término | Definición |
|---------|------------|
| **BPA** | Buenas Prácticas Ambientales - Normativa argentina para gestión de residuos peligrosos |
| **Constancia de Visita** | Documento que certifica que un técnico visitó una empresa en una fecha específica |
| **Checklist** | Formulario estructurado con preguntas específicas para auditar un aspecto (incendio, EPP, etc.) |
| **Informe Técnico** | Documento profesional que integra constancias, checklists y análisis del técnico |
| **Sede** | Ubicación física de una empresa (ej: planta, sucursal, depósito) |
| **HyS** | Higiene y Seguridad - Área de prevención de riesgos laborales |
| **EPP** | Equipos de Protección Personal (cascos, guantes, gafas, etc.) |
| **Soft Delete** | Eliminación lógica (marca activo=false) sin borrar físicamente el registro |
